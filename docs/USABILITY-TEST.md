# แผนทดสอบความใช้ง่าย (Usability Test) — ASTRA Motors

เอกสารนี้คือแผนทดสอบกับผู้ใช้จริง 5 คน ใช้เวลารวมประมาณครึ่งวัน (1 คน ประมาณ 45–50 นาที)
ครอบคลุม User Journey ทั้ง 7 ขั้นตอนตาม [`user-journey.md`](user-journey.md)
สถานะงานนี้ใน [`PROGRESS.md`](PROGRESS.md) คือ "ยังไม่ทำ"

- ระบบที่ทดสอบ: เว็บแอป ASTRA Motors (FastAPI + HTML/CSS/JS ธรรมดา + PostgreSQL/SQLite)
- URL ที่ใช้ทดสอบ: `http://localhost:8000`
- บัญชีตัวอย่างที่ระบบ seed ให้: `admin / admin1234`, `somchai / somchai123`, `nattaya / nattaya123`

## 1. เป้าหมายการทดสอบ

วัดว่า opportunity ที่ออกแบบไว้แก้ pain point ของ journey ได้จริงหรือไม่
คำถามวิจัย 5 ข้อ (ผูกกับ pain point แต่ละขั้น):

| # | คำถามวิจัย | Pain point ที่ผูกอยู่ | ขั้นของ journey | หน้าจอ/ไฟล์ที่เกี่ยวข้อง |
|---|---|---|---|---|
| RQ1 | ผู้ใช้หารถที่ตรงงบและตรงความต้องการ (เช่น ขับสี่ล้อ) ได้เองใน 2 นาทีไหม โดยไม่ต้องให้ช่วย | ข้อมูลกระจัดกระจาย เปรียบเทียบยาก / ตัวเลือกเยอะ ค้นหายาก | 1–2 | `frontend/index.html`, `frontend/js/home.js` |
| RQ2 | ข้อมูลในหน้ารายละเอียด (3D 360°, ราคาตามออปชัน, เทียบรุ่น, ค่างวด) พอให้ตัดสินใจไหม หรือยังรู้สึกว่าต้องไปถามโชว์รูม | ข้อมูลไม่ครบ ไม่มีรูปหลายมุม | 3 | `frontend/pages/model.html`, `compare.html`, `finance.html`, `thai-road.html` |
| RQ3 | ผู้ใช้จองทดลองขับออนไลน์สำเร็จโดยไม่ต้องโทรศัพท์ไหม และเข้าใจไหมว่าเวลาที่แสดงคือคิวว่างจริง | ต้องโทรจองเอง เวลาซ้ำกับลูกค้าอื่น | 4 | `frontend/pages/test-drive.html`, `backend/app/routers/showrooms.py`, `bookings.py` |
| RQ4 | ขั้นวางเงินจอง + อัปโหลดเอกสาร + ยื่นสินเชื่อ ผู้ใช้ทำจบในครั้งเดียวได้ไหม ติดที่จุดใดมากที่สุด | ขั้นตอนยุ่งยาก เอกสารเยอะ | 5 | `frontend/pages/reserve.html`, `loan.html`, `backend/app/routers/documents.py`, `loans.py` |
| RQ5 | ผู้ใช้รู้สถานะคำสั่งซื้อและรู้ว่าจะรีวิว/นัดเข้าศูนย์ได้ที่ไหน โดยไม่ต้องโทรถามไหม | ไม่รู้สถานะ ต้องโทรถาม / ไม่มีช่องทางรีวิว | 6–7 | `frontend/pages/status.html`, `after-sales.html`, `frontend/js/ui.js` (กระดิ่งแจ้งเตือน) |

สิ่งที่ **ไม่** อยู่ในขอบเขตการทดสอบครั้งนี้: ความสวยงามของกราฟิก, ประสิทธิภาพเซิร์ฟเวอร์,
การชำระเงินจริง (ระบบจำลอง), หน้าหลังบ้านของ admin (`backend/app/routers/admin.py` ยังเป็นงานใหม่)

## 2. ผู้เข้าร่วม

ใช้ผู้เข้าร่วม 5 คน ทดสอบทีละคน (one-on-one) ไม่ให้ดูกันเล่น

### เกณฑ์คัดเลือก

| เงื่อนไข | รายละเอียด |
|---|---|
| อายุ | 18 ปีขึ้นไป (ต้องมี/เคยมีใบขับขี่ เพราะระบบบังคับติ๊ก "มีใบขับขี่" ตอนจองทดลองขับ) |
| ประสบการณ์ซื้อรถ | อย่างน้อย 2 คนเคยไปโชว์รูมหรือเคยจองทดลองขับจริง (จะเทียบกับประสบการณ์เดิมได้) |
| ความชำนาญเว็บ | ผสม: 3 คนใช้เว็บคล่อง (ช้อปออนไลน์เป็นประจำ), 2 คนใช้เว็บไม่คล่อง |
| อุปกรณ์ที่คุ้นเคย | อย่างน้อย 2 คนที่ปกติใช้มือถือเป็นหลัก (ให้ทดสอบบนมือถือ) |
| ข้อห้าม | ห้ามเป็นคนที่เคยเห็นหรือช่วยพัฒนาเว็บนี้ และห้ามเป็นคนในกลุ่มโปรเจกต์ |

### ทำไม 5 คนถึงพอ

หลักของ Nielsen: ปัญหาการใช้งานส่วนใหญ่ถูกพบซ้ำ ๆ โดยผู้ใช้คนแรก ๆ ผู้ใช้ 5 คน
มักเจอปัญหาสำคัญได้ราว 80% ของทั้งหมด ส่วนคนที่ 6 ขึ้นไปจะเริ่มเจอปัญหาเดิมซ้ำ
งานทดสอบแบบนี้จึงคุ้มกว่าถ้าทำรอบเล็ก 5 คน แล้วแก้ แล้วทดสอบรอบสองอีก 5 คน
แทนการทำรอบเดียว 15 คน (เป้าหมายคือ "เจอปัญหาเพื่อแก้" ไม่ใช่ "วัดค่าทางสถิติ")

## 3. สิ่งที่ต้องเตรียม

### เครื่องและซอฟต์แวร์

- โน้ตบุ๊ก 1 เครื่องสำหรับผู้เข้าร่วม (หน้าจอ 13 นิ้วขึ้นไป) + เมาส์ภายนอก
- มือถือ 1 เครื่อง (สำหรับผู้เข้าร่วม 2 คนที่ทดสอบบนมือถือ)
  เข้า `http://<ip-ของโน้ตบุ๊ก>:8000` ผ่าน Wi-Fi เดียวกัน
- เบราว์เซอร์: Chrome เวอร์ชันล่าสุด เปิดหน้าต่างใหม่แบบ **ไม่มีส่วนขยาย**
  และล้างคุกกี้/localStorage ก่อนทุกคน
  (`localStorage` เก็บ token และรหัสจองแบบ guest — ถ้าไม่ล้าง คนถัดไปจะล็อกอินค้างเป็นคนก่อนหน้า)
- โน้ตบุ๊กของผู้ดำเนินการทดสอบอีกเครื่องสำหรับจดบันทึก (ไม่จดบนเครื่องที่ผู้ใช้ใช้)

### รันระบบ

วิธีที่ 1 — Docker (ตรงกับ README):

```bash
docker compose down -v        # ลบ volume db_data ให้ฐานข้อมูลสะอาด
docker compose up --build
```

วิธีที่ 2 — ไม่ใช้ Docker (SQLite):

```bash
rm -f backend/astra.db        # ลบฐานข้อมูลเก่า ระบบจะ seed ใหม่ตอนเริ่ม
pip install -r backend/requirements.txt
cd backend && uvicorn app.main:app --reload
```

### การขอความยินยอมบันทึกหน้าจอ

อ่านออกเสียงและให้เซ็นหรือพูดยืนยันก่อนเริ่ม (บันทึกเสียงยืนยันไว้ก็ได้):

> "เราขออนุญาตบันทึกหน้าจอและเสียงพูดระหว่างทดสอบ เพื่อใช้ทบทวนตอนสรุปผลเท่านั้น
> ไม่บันทึกใบหน้า ไม่เผยแพร่ต่อสาธารณะ ใช้ในรายงานวิชานี้อย่างเดียว และจะลบไฟล์เมื่อส่งงานเสร็จ
> คุณขอให้หยุดบันทึกหรือขอถอนตัวได้ตลอดเวลาโดยไม่ต้องให้เหตุผล"

ย้ำว่า **บัญชีและข้อมูลในระบบเป็นข้อมูลจำลองทั้งหมด** ไม่ต้องกรอกข้อมูลจริง
เลขบัตรประชาชน/รายได้ให้กรอกเป็นตัวเลขสมมุติ และการชำระเงินเป็นระบบจำลอง ไม่มีการตัดเงินจริง

## 4. งานที่ให้ผู้ใช้ทำ (Task Scenarios)

อ่านสถานการณ์ให้ฟัง + วางกระดาษที่พิมพ์สถานการณ์ไว้ข้าง ๆ **ห้ามบอกชื่อปุ่มหรือชื่อหน้า**
เวลาที่ระบุคือเวลาที่คาดว่าผู้ใช้ที่ทำได้ลื่นควรใช้ ถ้าเกิน 2 เท่า ให้ถือว่า "ติด" และจดเหตุผล
ถ้าเกิน 3 เท่าหรือผู้ใช้ขอความช่วยเหลือเกิน 2 ครั้ง ให้ปิดงานนั้นเป็น "ไม่สำเร็จ" แล้วไปงานถัดไป

### Task 1 — รับรู้ (ขั้นที่ 1)

> "คุณเพิ่งเปิดเว็บนี้ครั้งแรก เพื่อน ๆ บอกว่าช่วงนี้มีโปรโมชั่นรถหรู
> ลองดูว่าตอนนี้เว็บนี้มีข้อเสนออะไรอยู่ และคนที่ซื้อไปแล้วเขาพูดถึงรถพวกนี้ว่าอย่างไร"

- เกณฑ์สำเร็จ: ผู้ใช้พูดชื่อโปรโมชั่นที่กำลังใช้ได้อย่างน้อย 1 รายการ
  **และ** ชี้ส่วน "รีวิวจากสมาชิก" ได้ด้วยตัวเอง
- เวลาที่คาด: 1 นาที
- สิ่งที่จับตา: ผู้ใช้เลื่อนผ่านส่วนรีวิวไปเลยไหม, เข้าใจไหมว่าดาวบนการ์ดรถคือคะแนนรีวิว

### Task 2 — ค้นหารถ (ขั้นที่ 2)

> "คุณมีงบประมาณ 15 ล้านบาท อยากได้รถขับสี่ล้อเพราะบ้านอยู่ต่างจังหวัดฝนตกบ่อย
> ลองหาดูว่าเว็บนี้มีรุ่นไหนที่เข้าเกณฑ์ของคุณบ้าง แล้วบอกรุ่นที่คุณสนใจที่สุด 1 รุ่น"

- เกณฑ์สำเร็จ: ใช้ตัวกรองงบประมาณ **และ** ตัวกรองระบบขับเคลื่อน (ไม่ใช่ไล่อ่านการ์ดทีละใบ)
  แล้วระบุรุ่นได้ 1 รุ่น
- เวลาที่คาด: 1 นาที 30 วินาที
- สิ่งที่จับตา: หาแถบตัวกรองใต้หัวข้อ "ค้นหารุ่นที่ใช่" เจอไหม, งบ 15 ล้านตรงกับช่องตัวเลือกที่มีไหม,
  พิมพ์คำว่า "4 ล้อ" ลงช่องค้นหาแทนการใช้ตัวกรองไหม, รู้จักปุ่ม "ล้างตัวกรอง" ไหม

### Task 3 — ดูรายละเอียด (ขั้นที่ 3)

> "ก่อนตัดสินใจ คุณอยากรู้ว่ารถคันนี้สีอะไรสวยที่สุด ราคาจริงเมื่อใส่ออปชันที่คุณชอบเท่าไร
> คันนี้สู้กับอีกสองรุ่นที่คุณเคยคิดไว้ได้ไหม และถ้าผ่อน ค่างวดเดือนละประมาณเท่าไร"

- เกณฑ์สำเร็จ: เปลี่ยนสี/ออปชันแล้วอ่านราคาที่เปลี่ยนไปได้ถูก + เข้าหน้าเทียบรุ่นและใส่รถได้ 2 รุ่นขึ้นไป
  + ได้ตัวเลขค่างวดต่อเดือนจากหน้าคำนวณไฟแนนซ์
- เวลาที่คาด: 4 นาที
- สิ่งที่จับตา: หมุนโมเดล 3D เป็นไหม, รู้ไหมว่าออปชันบางอย่างทำให้ราคาขึ้น,
  หาทางไปหน้าเทียบรุ่น/คำนวณค่างวดเจอจากหน้ารายละเอียดไหม, สนใจหน้าจำลองถนนไทยไหม

### Task 4 — จองทดลองขับ (ขั้นที่ 4)

> "คุณอยากไปลองขับจริงที่โชว์รูมใกล้บ้านในสุดสัปดาห์นี้ ขอให้จัดการให้เรียบร้อยโดยไม่ต้องโทรหาใคร
> จบแล้วบอกด้วยว่าคุณต้องไปที่ไหน วันไหน กี่โมง"

- เกณฑ์สำเร็จ: ได้รหัสจอง `TD-xxxx-xxxxxx` จากปุ่ม "ยืนยันการจองทดลองขับ" และพูดซ้ำสาขา/วัน/เวลาได้ถูกต้อง
- เวลาที่คาด: 2 นาที 30 วินาที
- สิ่งที่จับตา: เข้าใจไหมว่าเวลาที่กดไม่ได้คือคิวที่คนอื่นจองแล้ว,
  สังเกตไหมว่าทำได้โดยไม่ต้องล็อกอิน (ระบบอนุญาตแบบ guest),
  เข้าใจช่องบังคับติ๊กว่ามีใบขับขี่ไหม (ถ้าไม่ติ๊กจะได้ข้อความ "ผู้ทดลองขับต้องมีใบขับขี่")

### Task 5 — ซื้อรถออนไลน์ (ขั้นที่ 5)

> "ขับแล้วถูกใจ คุณตัดสินใจเอารถคันนี้ แต่ยังไม่พร้อมจ่ายสด
> ขอให้วางเงินจองเพื่อล็อกราคาไว้ก่อน แล้วยื่นเรื่องขอสินเชื่อให้จบในวันนี้
> เอกสารที่ต้องใช้อยู่บนเดสก์ท็อปแล้ว ถ้าระบบถามหาบัญชี ใช้ชื่อ `somchai` รหัส `somchai123`"

- เกณฑ์สำเร็จ: ได้รหัสใบจอง `ADR-xxxx-xxxxxx` จากปุ่ม "ชำระเงินจองและออกใบจอง"
  + อัปโหลดเอกสารทั้ง 2 ประเภท (สำเนาบัตรประชาชน / หลักฐานรายได้) สำเร็จ
  + กด "ส่งคำขอสินเชื่อ" แล้วเห็นสถานะกำลังพิจารณา
- เวลาที่คาด: 7 นาที (ยังไม่รวมเวลารอผล 20 วินาที)
- สิ่งที่จับตา: ถึงจุดที่ต้องล็อกอินแล้วเกิดอะไรขึ้น, จำรหัสใบจองไปกรอกช่อง "รหัสใบจอง" หน้าสินเชื่อได้ไหม
  หรือลืม/พิมพ์ผิด, เลือกวิธีชำระ (QR พร้อมเพย์ / บัตรเครดิต-เดบิต) ได้ไหม,
  เข้าใจไหมว่าเงินจอง 200,000 บาทล็อกราคาไว้ 14 วัน

### Task 6 — ติดตามสถานะ (ขั้นที่ 6)

> "ผ่านไปครึ่งชั่วโมง คุณอยากรู้ว่าเรื่องที่ยื่นไปคืบหน้าถึงไหน และตกลงสินเชื่อผ่านหรือไม่
> ถ้าผ่านแล้ว ขอให้นัดวันไปรับรถด้วย"

- เกณฑ์สำเร็จ: เปิดหน้า "การจองของฉัน" ได้เอง อ่านผลสินเชื่อออก และนัดรับรถสำเร็จ
  (ถ้าผลไม่อนุมัติ ถือว่าสำเร็จเมื่อผู้ใช้อธิบายทางเลือกที่ระบบเสนอได้)
- เวลาที่คาด: 2 นาที 30 วินาที
- สิ่งที่จับตา: ใช้กระดิ่งแจ้งเตือนหรือเดาว่าต้องไปหน้าไหน, รู้สึกว่ารอนานไหม,
  ใช้ช่องพับ "ค้นหาด้วยรหัสใบจอง" หรือใช้รายการที่ระบบดึงมาจากบัญชีให้แล้ว, อ่าน stepper เข้าใจไหม

### Task 7 — หลังการขาย (ขั้นที่ 7)

> "สองเดือนผ่านไป คุณขับมาแล้วหลายพันกิโลเมตร อยากบอกคนอื่นว่ารถคันนี้เป็นอย่างไร
> แล้วถึงรอบเช็กระยะ อยากนัดเข้าศูนย์ด้วย เห็นว่ามีคะแนนสะสมอยู่ ลองดูว่าเอาไปทำอะไรได้"

- เกณฑ์สำเร็จ: เขียนรีวิวให้ดาวสำเร็จ 1 รีวิว + กด "ยืนยันนัดหมาย" เข้าศูนย์บริการสำเร็จ 1 นัด
  + บอกได้ว่าตอนนี้มีคะแนนเท่าไรและแลกของรางวัลอะไรได้
- เวลาที่คาด: 4 นาที
- สิ่งที่จับตา: หาหน้าหลังการขายเจอไหม, สับสนระหว่างรีวิวในหน้ารุ่นกับแท็บ "รีวิวของฉัน" ไหม,
  เข้าใจไหมว่าคะแนนมาจากไหน (ระบบบวกให้เองจาก event ไม่ได้กดรับเอง)

เวลารวมของ 7 งานที่คาดไว้ประมาณ 22–25 นาที เหลือเวลาสำหรับแนะนำตัว SUS และคำถามปิดท้าย

## 5. ตัววัดผล

| ตัววัด | วิธีเก็บ | เกณฑ์ที่ถือว่าผ่าน |
|---|---|---|
| Task success rate | นับต่อ task: สำเร็จ = 1, สำเร็จแต่ต้องช่วย = 0.5, ไม่สำเร็จ = 0 | 80% ขึ้นไปต่อ task (คือ 4 จาก 5 คน) |
| Time on task | จับเวลาจากที่อ่านสถานการณ์จบ ถึงผู้ใช้บอกว่าเสร็จ | ไม่เกิน 2 เท่าของเวลาที่คาดในส่วนที่ 4 |
| จำนวนครั้งที่ขอความช่วยเหลือ | นับทุกครั้งที่ผู้ใช้ถามหาทางหรือผู้ดำเนินการต้องใบ้ | ค่าเฉลี่ยไม่เกิน 0.5 ครั้ง/task |
| จำนวน error | นับการกระทำที่ผิดทาง: กดผิดหน้า, ฟอร์มถูกปฏิเสธ, ข้อความ error ของระบบ | ค่าเฉลี่ยไม่เกิน 1 ครั้ง/task |
| SEQ (Single Ease Question) | ถามทันทีหลังจบแต่ละ task | ค่าเฉลี่ย 5.5 ขึ้นไปจาก 7 |
| SUS | ตอบ 10 ข้อตอนจบทั้งหมด | คะแนนรวมเฉลี่ย 68 ขึ้นไป |

### SEQ — ถามหลังจบทุก task

> "โดยรวม งานที่เพิ่งทำนี้ยากหรือง่ายแค่ไหน ให้คะแนน 1 ถึง 7 โดย 1 = ยากมาก, 7 = ง่ายมาก"

ถ้าได้ 4 หรือต่ำกว่า ให้ถามต่อ 1 คำถาม: "ตรงไหนที่ทำให้มันยาก" แล้วจดคำตอบดิบ ๆ

### SUS 10 ข้อ (ฉบับไทย)

ให้ตอบทุกข้อด้วยสเกล 1–5 โดย **1 = ไม่เห็นด้วยอย่างยิ่ง, 5 = เห็นด้วยอย่างยิ่ง**
ให้ผู้ใช้ตอบเอง อย่าอ่านออกเสียงแล้วตีความแทน

| ข้อ | ข้อความ | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 1 | ฉันคิดว่าฉันอยากกลับมาใช้เว็บนี้อีกบ่อย ๆ | | | | | |
| 2 | ฉันรู้สึกว่าเว็บนี้ซับซ้อนเกินความจำเป็น | | | | | |
| 3 | ฉันคิดว่าเว็บนี้ใช้งานง่าย | | | | | |
| 4 | ฉันคิดว่าฉันต้องมีคนช่วยหรือมีผู้เชี่ยวชาญคอยแนะนำจึงจะใช้เว็บนี้ได้ | | | | | |
| 5 | ฉันรู้สึกว่าส่วนต่าง ๆ ของเว็บนี้ทำงานเข้ากันดี | | | | | |
| 6 | ฉันคิดว่าเว็บนี้มีความไม่สอดคล้องกันอยู่หลายจุด | | | | | |
| 7 | ฉันคิดว่าคนทั่วไปจะเรียนรู้การใช้เว็บนี้ได้เร็ว | | | | | |
| 8 | ฉันรู้สึกว่าเว็บนี้ใช้งานยุ่งยากและเทอะทะ | | | | | |
| 9 | ฉันรู้สึกมั่นใจเวลาใช้งานเว็บนี้ | | | | | |
| 10 | ฉันต้องเรียนรู้อะไรหลายอย่างก่อนจะเริ่มใช้เว็บนี้ได้ | | | | | |

วิธีคิดคะแนน SUS:

1. ข้อเลขคี่ (1, 3, 5, 7, 9): คะแนนที่ใช้ = คำตอบ − 1
2. ข้อเลขคู่ (2, 4, 6, 8, 10): คะแนนที่ใช้ = 5 − คำตอบ
3. บวกคะแนนที่ใช้ทั้ง 10 ข้อ (ได้ 0–40) แล้วคูณ 2.5 จะได้คะแนน SUS ช่วง 0–100
4. คะแนน SUS ของระบบ = ค่าเฉลี่ยของผู้เข้าร่วมทั้ง 5 คน

การแปลผลคร่าว ๆ: ต่ำกว่า 50 = แย่, 50–67 = ต้องปรับปรุง, 68 = ค่ากลางของระบบทั่วไป,
69–80 = ดี, มากกว่า 80 = ดีมาก
หมายเหตุ: SUS ไม่ใช่เปอร์เซ็นต์ ห้ามเขียนรายงานว่า "ผู้ใช้พอใจ 72%"

## 6. สคริปต์ผู้ดำเนินการทดสอบ

### คำพูดเปิด (อ่านตามนี้ให้เหมือนกันทุกคน)

> "ขอบคุณที่มาช่วยนะครับ/ค่ะ วันนี้เราทดสอบ **เว็บไซต์** ไม่ได้ทดสอบคุณ
> ถ้าคุณทำอะไรไม่ได้ แปลว่าเว็บเราออกแบบไม่ดีพอ ซึ่งเป็นสิ่งที่เราอยากรู้
> เว็บนี้เป็นงานในวิชาเรียน ผมไม่ได้เป็นคนขายรถ ไม่ต้องเกรงใจ ติได้เต็มที่
> เดี๋ยวผมจะอ่านสถานการณ์ให้ฟังทีละงาน รวม 7 งาน ใช้เวลาประมาณครึ่งชั่วโมง
> ระหว่างทำ ขอให้ **พูดออกมาว่าคุณกำลังคิดอะไร** กำลังมองหาอะไร คาดว่ากดแล้วจะเกิดอะไร
> ถ้าคุณเงียบไป ผมจะถามว่าตอนนี้คิดอะไรอยู่ ไม่ได้จะเร่งนะครับ
> ข้อมูลทุกอย่างในระบบเป็นข้อมูลจำลอง ไม่ต้องใส่ข้อมูลจริงของคุณ
> เริ่มเลยนะครับ มีคำถามก่อนไหม"

### กติกา think-aloud

- ให้ผู้ใช้เล่าสิ่งที่คิดตลอด ถ้าเงียบเกินประมาณ 15 วินาที ใช้ประโยคกลาง ๆ ว่า "ตอนนี้คิดอะไรอยู่ครับ"
- ผู้ใช้ถามว่าต้องกดอะไร ให้โยนกลับ: "ถ้าอยู่บ้านคุณจะทำอย่างไรต่อครับ"
- ผู้ใช้ติดหนัก (เกิน 2 เท่าของเวลาที่คาด หรือขอช่วยครั้งที่ 3) ให้บันทึกว่าไม่สำเร็จ แล้วพูดว่า
  "งานนี้พอแค่นี้ก่อนครับ ไปงานถัดไปกัน" ถ้าจำเป็นต่อการทำงานถัดไป ค่อยพาไปหน้าที่ควรไปถึง
- จดคำพูดดิบ ๆ อย่าแปลเป็นข้อสรุปตอนจด เช่น จด "กดแล้วมันเงียบไป" ไม่ใช่ "ผู้ใช้ไม่เห็น feedback"

### ประโยคที่ห้ามพูด

| ห้ามพูด | เพราะอะไร | พูดแบบนี้แทน |
|---|---|---|
| "กดปุ่มมุมขวาสิ" / "เลื่อนลงหน่อย" | ชี้ทาง ทำให้ไม่เห็นปัญหาจริง | "คุณคิดว่าจะหาได้จากตรงไหนครับ" |
| "ใช่แล้ว ถูกต้อง" / "เยี่ยม" | ให้รางวัลเฉพาะทางที่เราคาด ผู้ใช้จะเดาใจเรา | "โอเคครับ" (เสียงเรียบ ๆ) |
| "ไม่ใช่ครับ ไม่ใช่ตรงนั้น" | ทำให้ผู้ใช้กลัวผิดและหยุดสำรวจ | เงียบ ปล่อยให้ผู้ใช้ลองต่อ |
| "เมนูนี้มันอยู่ในหน้าหลังการขายครับ" | เฉลยโครงสร้างเว็บ | "คุณคาดว่าเรื่องนี้ควรอยู่หน้าไหนครับ" |
| "ปกติฟีเจอร์นี้มันทำงานได้นะ แปลกจริง" | แก้ตัวให้ระบบ ผู้ใช้จะเลิกติ | "ขอบคุณครับ เดี๋ยวจดไว้" |
| "คุณคิดว่าถ้าแก้เป็นแบบ X จะดีกว่าไหม" | ชี้นำคำตอบ (leading question) | "ถ้าให้คุณแก้ตรงนี้ คุณจะแก้อะไร" |

### คำถามปิดท้าย 3 ข้อ (ถามหลังตอบ SUS เสร็จ)

1. "ถ้าตัดเรื่องความสวยงามออก **จุดที่น่าหงุดหงิดที่สุด** วันนี้คือตรงไหนครับ และเพราะอะไร"
2. "ถ้าเว็บนี้มีอยู่จริงวันนี้ คุณจะใช้มันแทนการโทรหาโชว์รูมไหม ขั้นไหนที่คุณยังอยากโทรคุยกับคนจริง"
3. "มีอะไรที่คุณคาดว่าจะเจอบนเว็บนี้แต่หาไม่เจอไหมครับ"

## 8. วิธีสรุปผล

### ขั้นตอน

1. รวมบันทึกทั้ง 5 ชุด ทำตารางสรุป: task success rate, ค่าเฉลี่ย time on task, SEQ, SUS
2. ดึงปัญหาที่สังเกตได้ออกมาเป็นรายการเดี่ยว ๆ (1 อาการ = 1 บรรทัด) ยังไม่ต้องตัดสินอะไร
3. จับปัญหาที่เป็นเรื่องเดียวกันจากหลายคนมารวมเป็น finding เดียว แล้วนับว่าเจอกี่คน
4. ให้ระดับความรุนแรงตามตารางด้านล่าง
5. เรียงลำดับแก้: ระดับ 3 ก่อน แล้วระดับ 2 ที่เจอ 3 คนขึ้นไป แล้วที่เหลือ
6. เขียนผลลง `docs/PROGRESS.md` (เปลี่ยนสถานะบรรทัด "Usability test กับผู้ใช้จริง") และเปิด issue ตาม finding

|---|---|---|
| 0 | ไม่ใช่ปัญหาการใช้งาน เป็นความชอบส่วนตัวหรือข้อเสนอฟีเจอร์เพิ่ม | "อยากให้มีสีแดงเพิ่ม" |
| 1 | ปัญหาผิวเผิน ผู้ใช้สะดุดแต่แก้ได้เองในไม่กี่วินาที แก้ได้ถ้าเหลือเวลา | คำบนปุ่มอ่านครั้งแรกไม่เข้าใจแต่เดาถูก |

### ข้อควรระวังตอนตีความ

- H3 และ H4 เป็นพฤติกรรมที่ออกแบบไว้ (จำลองการพิจารณา + polling) ไม่ใช่บั๊ก
  แต่ถ้าผู้ใช้เข้าใจผิดจริง ก็ยังนับเป็นปัญหา usability และแก้ด้วยการสื่อสารบนหน้าจอได้
- ห้ามสรุปเรื่องที่ระบบยังไม่มี เช่น การชำระเงินจริง อีเมล/SMS จริง วิดีโอรถ
  หรือหน้าหลังบ้านพนักงานโชว์รูม — ของพวกนี้อยู่ในหัวข้อ "ส่วนที่ยังไม่เสร็จ" ของ `PROGRESS.md` แล้ว
- ถ้าเจอบั๊กจริง (ระบบ error 500, ข้อมูลไม่ตรง) ให้แยกบันทึกเป็นบั๊ก ไม่นับรวมกับ finding ด้าน usability
